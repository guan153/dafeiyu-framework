<p align="center"><img src="assets/dafeiyu.png" width="260" alt="大肥鱼"></p>

## 项目介绍

先说人话：这套东西不是一只完整的机器人，也不是一个"情绪大模型"。

它是一层情绪底座，负责回答三个问题：她现在到底是什么心情？这个心情是怎么来的？接下来她该怎么说话、该不该主动开口？

你把它接到自己的聊天程序下面，它就能给上面的对话层提供一份"她现在是谁"的说明；你不接，它自己不会聊天，也不会回消息。

很多陪伴机器人，情绪是"演"出来的。用户说一句话，程序拼一段提示词："你现在有点黏人，有点委屈，回他一句。"模型演得很好，但下一句可能就变了；昨天发生的事，今天进不了她的心情；你也没法解释她为什么突然冷淡。

我们想解决的就是这个。不是让模型演得更像，而是让她真的有一份连续的情绪状态。

### 现在大多数做法，问题出在哪

第一个问题，一轮里好几个心情。

聊天的地方判断一次，表情的地方判断一次，主动的地方又判断一次，最后全塞进同一段提示词。结果就是嘴上说黏人，表情是平静，主动模块读到的又是安心。模型不知道信谁，人也不知道信谁。

第二个问题，情绪只有一个标签。

开心、难过、平静，这种标签能说方向，说不了层次。同样是开心，有人是松了一口气，有人是想跳起来；同样是难过，有人想说话，有人只想消失。只有一个标签，写出来的人就会很扁。

第三个问题，情绪没有积累。

一条消息进来判断一次，下一条重新判断。昨天被冷落、上周聊得很晚、长期的关系，都进不了"此刻"。她永远像刚认识你，或者每次都重新开局。

第四个问题，错了退不回去。

情绪写死在代码里，或者散在好几段提示词里。发现她今天太黏，只能改代码、重启、再看；想只关掉表情、保留语气，做不到；想回到昨天的状态，也没有开关。

这四个问题，不是提示词写得不好，是情绪没有一个"说了算"的地方。

### 我们怎么做

我们只做了一件事：让情绪有一个唯一的来源。

具体说，就是一份文件，`emotion_snapshot.json`。同一时间，只允许一个地方写它；其他地方只能读，不能改。

这份文件里写的不是"她应该怎么说话"，而是"她现在是什么状态"：什么心情、强度多少、开心还是难受、累不累、想不想靠近、想不想说话。

然后，状态块、表情、语气、动作、主动程度，全都读这一份文件。它们可以有不同的表现，但不能有不同的"事实"。这样就不会出现"嘴上黏人、表情平静"。

网关也一样。模型调用之前，网关会再读一次这份文件，把情绪写进提示词。它不是再判断一次，而是读同一份。这样一轮对话里，不会出现两个心情。

这份文件每 60 秒更新一次。更新它的地方只有一个，叫 `whale_affect`；别的模块只能提交"我看到了什么"，不能直接改。这个规矩听起来很死，但它解决了最难查的一类问题：多个地方同时写，最后谁也不知道当前值是谁写的。

### 一条消息进来，到底发生什么

用户在 QQ 上发一句"在吗"。

第一步，先判断这句话大概是什么情绪。本地有一个 laya 分类器，8 个类别：兴奋、吃醋、平静、开心、撒娇、生气、疲惫、难过。它跑在 CPU 上，一次大概 90 毫秒，不花 API 的钱。它只是给一个参考，不是最终结论；置信度低就回退词表，分类器挂了也不影响聊天。

第二步，读当前的情绪文件。如果文件过期了，超过 300 秒，读的地方会自动退回旧逻辑，不会卡住回复。

第三步，拼提示词。人格、说话规矩、当前状态、记忆、表达方式，按预算往里放。预算是 6000 字，超了要报警，不能偷偷塞。

第四步，网关把同一份情绪再读一遍，写进系统提示词。

第五步，模型生成回复，分段发出去。第一句多快发、一段多长、要不要带表情，都是情绪文件里的系数决定的。

第六步，这句话、这个反应、这段时间，会重新更新情绪。下一次 60 秒到点，写一份新的文件，版本号加一。

整个流程里，模型只负责"怎么说"；"她此刻是谁"，由那份文件负责。

### 情绪不是一条消息决定的

这份文件里不只有"心情"两个字。

它还有效价，就是开心还是难受；有唤醒，就是平静还是激动；有四个慢变量：羁绊、存在感、被需要感、精力。

羁绊是长时间聊出来的，不是一句"在吗"就能满；存在感是被忽略会掉的；被需要感是被依赖会涨的；精力会随着时间掉，休息会回来。

这些变量变得很慢，所以她才会有连续性。不是每条消息重新开局，而是"这段时间把她推到了这里"。

举个例子。一个安静的下午，没人说话，她的精力在掉，羁绊没掉，存在感有点空。这时候有人发"在吗"。她不是突然决定"我要黏人"，是这段时间本来就把她推到了黏人。文件里可能写着：心情黏人，强度 0.511，效价 -0.123，唤醒 0.511，羁绊 96，精力 51.7。

这些数字不是给人看的，是给读的地方用的。状态块读它，表情读它，主动闸门也读它。

### 情绪会进记忆

这一点很重要，也是下一版要重点做的。

情绪文件会过期，但情绪不会凭空消失。那些印象很深的事，会被写进记忆：被夸、被冷落、一次聊了很久的对话、一个突然的转折。

这些记忆不是"聊天记录"。聊天记录记的是"她说了什么"，情绪记忆记的是"那件事让她处在什么状态"。

下次想起这件事，不是复读当时的话，是想起当时的感觉。所以她会在一个看起来毫无关系的瞬间，突然安静下来，或者突然想靠近。

不是所有事都值得记。我们会按印象深不深、情绪强不强、关系有没有变化、这件事重复过几次来筛。记住的是"那段时间她是怎么过来的"，不是"昨天第三句说了什么"。

现在这一版，情绪内核里已经有羁绊、存在感、精力这些慢变量，也有情绪峰值和记忆召回；印象深的事会进峰值，之后被想起来，会影响下一轮的心情。

但是"情绪曲线写进长期记忆，再按心情召回"这条完整的路，还在下一版。

下一版想做的，是让她记住"那段时间我是什么状态、因为什么、后来怎么缓过来的"，而不是只记住"那天他说了什么"。这样她再想起一段日子，想起的是当时的温度，不是一句台词。

这一版先把情绪文件做对；下一版，再让她真的记住自己是怎么走过来的。

### 说话为什么更像人

不是形容词多就叫细腻。

第一，事实要一致。心情、表情、语气、动作，读的是同一份情绪。不能嘴上黏人，表情平静。

第二，层次要够。底色是主心情，温度是强度，表达是眼睛、尾巴、语气词、口癖，场景决定长短，关系决定她提不提以前的事。

第三，要允许留白。可以碎，可以停一半，可以说"算了"。不是每句都要完整、漂亮、有信息量。

真实聊天里，她的回复长度中位数是 12.5 个字，15 个字以内的占 90.9%。语气词出现的行数占 45.5%。这些不是拍脑袋，是拿真实回复统计的。

但问题也有：句号收尾率还是 100%，短句不该每句都有句号；固定填充词"嗯"还是占到 40.9%，换词没换习惯。这些都知道，没修好就是没修好，不粉饰。

### 主动，不是乱发消息

主动不是定时器，也不是随机。

流程是：先看情绪，算出"她现在有多想说"，这叫 want；再看阈值，过线了才考虑开口；然后过闸门，看配额、看是不是静默时段、看上次开口有没有人理；最后才决定发不发。

情绪低的时候，want 低，闸门直接拒绝；情绪高的时候，也要过配额，不能刷屏。

这份情绪文件里，有几个系数直接参与：主动倾向、开新话题的倾向、回避倾向、回复长度、第一句的延迟、表情密度。

默认策略是保守的。多数主动开口的通道是关着的，或者在影子模式里观察，不真的发。不是不能主动，是宁可少说，也不刷屏。

### 花多少钱，多快

情绪分类是本地 CPU 跑的，一次 90 毫秒左右，不花 API 的钱。

网关每次请求有固定开销，大概 219 个 token。真实一轮对话，注入的内容大概 4700 个 token，输出几百个 token。按 DeepSeek 现在的价格算，一条回复大概 6 厘到 1 分 3；一千条大概 6 到 13 块钱。缓存命中的话更便宜。

延迟方面，分类 90 毫秒，网关注入加短请求 1 秒左右，真实一轮 12 到 28 秒。这 12 到 28 秒主要花在模型生成和分段上，不是情绪计算。情绪这一层本身很轻。

### 跟别的做法比，强在哪

多模块拼情绪，容易一轮好几个心情；我们只有一个地方写，其他地方读同一份。

只靠提示词演，情绪不可查、不可回滚；我们有文件、有版本、有开关。

云端情绪接口，多一次网络、多一份黑箱；我们在本地，90 毫秒，不花 API 钱。

单一标签，表达会扁；我们分底色、温度、表达、场景、关系。

定时器主动，容易刷屏；我们用情绪积分、闸门、配额。

最核心的区别是：别人在调"怎么让模型演得更像"，我们在管"她此刻到底是什么心情、为什么、错了能不能退回去"。

### 最强的地方

一是情绪一致。所有地方读同一份文件，不会一轮三个心情。

二是情绪有积累。羁绊、存在感、精力这些慢变量，不是一条消息就重置。

三是情绪能进记忆。印象深的事会留下来，之后想起来会影响心情；这一版打了底，下一版做完整。

四是话术有层次。不是一套模板，是底色、温度、表达、场景、关系一起决定。

五是主动可控。不是定时器，是情绪、闸门、配额一起决定。

六是成本可控。本地分类不花钱，情绪文件按需注入，缓存前缀能省输入。

七是能回滚。改一个 JSON，5 秒生效，不用改代码、不用重启。

八是能验证。情绪文件、日志、闸门记录、网关的请求数，都能查。

### 这套东西不适合谁

不适合想 clone 下来一键就能聊天的人。它没有完整的聊天程序，也没有账号和模型。

不适合想直接放到公网的人。它默认只在本机跑，没有登录、没有鉴权。

不适合只要一个"很会演"的提示词的人。它管的是状态，不是文案。

它适合已经有自己的聊天程序、想接一层情绪底座的人；适合想研究"情绪怎么长期存在"的人；适合对可回滚、可观测有执念的人。

### 最后

我们不想做一个"每次都很像人"的模型。

我们想做一个每次都能解释自己为什么这样的角色。

她可以有情绪，但情绪有出处；她可以主动，但主动有闸门；她可以忘记，但记忆有索引；她可以出错，但错误能退回去。

这就是这份仓库想做的事。
## 一句话

**不是让模型"演"情绪，而是先有一份可审计的情绪事实，再让表达层去读它。**

## 情绪闭环是什么

```
情感分类器（laya）──┐
身体/内感受/事件 ────┼──> whale_affect ──写──> emotion_snapshot.json
                    │                              │
                    └──> moodfusion（底色/温度/表达）│
                                                   ├── state_bus（状态块）
                                                   ├── brain（<psyche>）
                                                   ├── face（表情/语气）
                                                   ├── meme（表情出口）
                                                   ├── urge（欲望）
                                                   └── expression gate（开口闸门）
                                                   │
                                                   ▼
                                        gateway（8920）读同一快照
                                                   │
                                                   ▼
                                       上层运行时拿到一份情绪
```

核心规则：

1. **单写者**：只有 `whale_affect` 能写 `emotion_snapshot.json`。
2. **读方统一**：其余模块通过 `shadow_switches.json` 读同一快照。
3. **网关同源**：8920 也读快照，避免 prompt 里出现两个心情。
4. **可回滚**：每个读方一个开关，改 JSON 即可回退。
5. **可验收**：影子日志、`voice_gate.json`、快照时间戳都能直接查。

## 相比常见做法的优势

| 常见做法 | 问题 | 我们的做法 |
|---|---|---|
| 每个模块自己算情绪 | 一轮 prompt 出现"黏人/安心/平静"多个心情 | 单写者 + 统一快照 |
| 只靠 prompt 让模型演 | 不可审计、不可回滚 | 状态机 + 快照 + 闸门 |
| 情绪只有一档标签 | 表达扁平 | 底色/温度/表达分层 |
| 云端黑箱 | 隐私与成本不可控 | 本地网关，127.0.0.1 |
| 规则硬编码 | 改一处崩一片 | 开关集中到 JSON，热读 |
| 只看"像不像" | 无法定位 | 影子日志 + 证据 gate |

更完整的对比见 [docs/WHY-OURS.md](docs/WHY-OURS.md)。

## 我们到底强在哪（一句话版）

- **一致**：一份情绪事实，所有读方和网关读同一份，不会一轮三个心情。
- **可回滚**：每个读方一个 JSON 开关，5 秒热读，不用改代码。
- **可审计**：快照、影子日志、闸门 JSON、网关 requests/injected 都能查。
- **有层次**：底色/温度/表达/扰动，不是单一标签。
- **便宜**：本地分类不花 API 钱；按需注入，输入成本可控。
- **不装**：分类器只做输入，低置信回退；做不到就承认。

## 快速开始

```powershell
git clone https://github.com/guan153/dafeiyu-framework.git
cd dafeiyu-framework

# 1) 环境变量（不要写死密钥）
$env:LAYA_HOME="C:\path\to\laya"
$env:EMOTION_CLS_MODEL="C:\path\to\emotion_cls.pt"
$env:BEAM_SECRETS_FILE="C:\path\to\gateway_secrets.json"

# 2) 启动 laya 情感分类器（8901）
python laya_emotion/emotion_server.py --port 8901 --device cpu

# 3) 启动 BEAM 网关（8920）
python gateway/beam_gateway.py

# 4) 验证
curl http://127.0.0.1:8901/health
curl http://127.0.0.1:8920/health
curl -X POST http://127.0.0.1:8901/classify -H "Content-Type: application/json" -d '{"text":"今天有点累"}'
```

各组件没有内置守护；生产使用请自己加进程管理。

## laya 情感分类器改装（重点）

- 基座：`convaiinnovations/laya` multilingual encoder
- 分类头：768 → 8 类线性层（兴奋 / 吃醋 / 平静 / 开心 / 撒娇 / 生气 / 疲惫 / 难过）
- 默认 CPU，省显存；`--device cuda` 可切
- HTTP：`POST /classify`，返回 `label / confidence / probs`
- 改装点：问候词纠正（"在吗"别判成撒娇）、低置信回退词表、CPU 常驻、8 类映射到 `goal_congruence`

详见 [docs/LAYA-EMOTION.md](docs/LAYA-EMOTION.md)。

> **模型包说明**：GitHub 仓库树只带 26KB 分类头；完整模型（laya encoder 614MB + tokenizer 32.8MB + 8 类头，共 599MB zip）在 [Release v0.1.0-laya-model](https://github.com/guan153/dafeiyu-framework/releases/tag/v0.1.0-laya-model) 下载。代码会优先读包内 laya_emotion/model/laya/multilingual/，没有才回退到 Hugging Face。
