## 二、价格：到底花在哪

### 2.1 官方单价（deepseek-flash）

| 项目 | 谷时（USD/1M） | 峰时（USD/1M） |
|---|---|---|
| 输入（缓存命中） | 0.003 | 0.006 |
| 输入（缓存未命中） | 0.15 | 0.30 |
| 输出 | 0.60 | 1.20 |

- 峰时：UTC 01:00–04:00、06:00–10:00，周一至周五，排除中国法定节假日。
- 换算北京时间：**09:00–12:00、14:00–18:00**。
- 其余时间（含周末、节假日）为谷时，约为峰时一半。
- 汇率按 **1 USD ≈ 7.2 CNY** 估算，实际以账单为准。

### 2.2 单条回复怎么算

公式：

```
费用 = 输入tokens × 输入单价 + 输出tokens × 输出单价
```

示例 A：短消息

- 输入 219 tokens，输出 16 tokens，峰时未命中缓存：
  - 219 × 0.30 / 1,000,000 = $0.0000657
  - 16 × 1.20 / 1,000,000 = $0.0000192
  - 合计 **$0.000085 ≈ ¥0.0006**

示例 B：真实一轮（估算）

- 输入 4,700 tokens，输出 300 tokens，峰时未命中缓存：
  - 4,700 × 0.30 / 1,000,000 = $0.00141
  - 300 × 1.20 / 1,000,000 = $0.00036
  - 合计 **$0.00177 ≈ ¥0.0127**
- 谷时约 **¥0.0064**
- 1,000 轮：峰时约 **¥12.7**，谷时约 **¥6.4**

示例 C：缓存命中

- 输入 4,700 tokens 全部命中缓存，峰时：
  - 4,700 × 0.006 / 1,000,000 = $0.0000282
  - 输出 300 × 1.20 / 1,000,000 = $0.00036
  - 合计 **$0.00039 ≈ ¥0.0028**
- 缓存命中能把输入成本压到接近零，**输出才是主要成本**。

### 2.3 为什么便宜/为什么可能变贵

**便宜的原因**

- 情绪快照只有 681 B，读它不花 token。
- laya 是本地 CPU，**分类不产生 API 费用**。
- 网关只注入必要的底色，不把整份状态塞进去。
- 读方可以只读快照的少量字段，而不是整份历史。

**可能变贵的原因**

- 上下文越长，输入 tokens 越多；7,524 字注入约 4,700 tokens。
- 多轮对话不带缓存，输入重复计费。
- 输出越长，费用越高（输出单价是输入未命中的 4 倍）。
- 峰时价格是谷时 2 倍。

### 2.4 成本优化清单

1. **优先谷时**：能等的非实时任务放到谷时。
2. **控制注入预算**：6,000 字是硬上限；实测有 7,524 字超预算，应该压缩。
3. **复用前缀缓存**：system/人格/规则放在稳定前缀，别每轮变。
4. **只注入需要的字段**：不要整份快照+整份记忆一起塞。
5. **本地分类器兜底**：分类不花 API 钱。
6. **输出限长**：聊天句长短，输出 tokens 自然低。

## 三、Token：一份 prompt 里有什么

### 3.1 实测

- 5,640 汉字 → 3,568 prompt tokens（含网关固定块）。
- 219 tokens 是网关固定系统块（短请求实测）。
- 比例约 **0.63 token/汉字**；英文/符号/代码会不同。

### 3.2 真实一轮的构成（估算）

| 部分 | 字符 | tokens（估） |
|---|---|---|
| 人格/规则 | 3,317 | ~2,100 |
| 语感规范 | 668 | ~420 |
| 状态块 | 1,025 | ~650 |
| 情绪/表情 | 264 | ~170 |
| 记忆/上下文 | 3,247 | ~2,050 |
| 网关底色 | — | 219 |
| 合计 | ~7,500 | **~4,700–5,000** |

> 这些数字来自日志里的字符数，tokens 按 0.63 比例估算；不同分词器会有偏差。

### 3.3 省 token 的架构设计

- **快照是文件，不是 prompt**：读它不花钱，只有注入的字段花 token。
- **分类器本地**：laya 推理不产生 API tokens。
- **分层注入**：状态/情绪/记忆分开，按需裁剪。
- **硬预算**：6,000 字上限，超了要报警。
- **前缀稳定**：人格/规则放最前，缓存命中率高。

## 四、延迟：12–28 秒花在哪

### 4.1 实测拆解

| 阶段 | 实测 | 说明 |
|---|---|---|
| laya 分类 | 90ms p50 / 116ms p90 | CPU，本地 |
| 网关转发 | 1.0–1.2s | 短请求，含注入 |
| 模型生成 | 数秒–十几秒 | 取决于上下文/输出/负载 |
| 分段/打字延迟 | 数秒 | 让回复像人，不是瞬间刷屏 |
| 端到端 | **12–28s** | 真实 QQ 一轮 |

### 4.2 为什么不是"秒回"

- 人说话本来就有停顿；瞬间长段回复反而假。
- 上下文越长，模型 prefill 越慢。
- 分段发送让每段像一句话，而不是一堵墙。
- 网关是单点；它挂了，延迟直接失败。

### 4.3 能优化的部分

- 缩短注入（6,000 字以内）。
- 把稳定前缀放前面，提高缓存命中。
- 限制输出长度，减少 decode 时间。
- 非实时任务避峰。
- 网关加健康检查/重连，减少失败等待。

## 五、话术细腻：不是形容词多，是一致性

### 5.1 机制

一条回复的"细腻"来自五层：

1. **底色**：当前主情绪（如"黏人"）。
2. **温度**：强度/唤醒，决定语气软硬。
3. **表达**：眼睛、尾巴、语气词、颜文字、口癖。
4. **场景**：聊天/安慰/撒娇，决定句子长短和停顿。
5. **关系**：记忆、称呼、最近发生的事。

这五层都读同一份情绪快照，所以不会"嘴上说黏人，表情是平静"。

### 5.2 实测指标（真实对话样本）

| 指标 | 当前 | 说明 |
|---|---|---|
| 长度中位数 | 12.5 字 | 接近短句聊天 |
| ≤15 字占比 | 90.9% | 不写小作文 |
| 语气词行占比 | 45.5% | 偏高，仍在调 |
| 句号收尾率 | 100% | **已知问题**，短句不该都有句号 |
| 固定填充词"嗯" | 40.9% | **已知问题**，换词没换习惯 |
| 相邻 7 字复读 | 0 | 指标失效，改用固定填充词密度 |
| 分析腔词 | 0 | 没有"这组对照说明问题"这类 |

### 5.3 细腻的边界

- 细腻不等于每句都漂亮；允许碎、允许停一半。
- 细腻不等于长；短句也可以有情绪。
- 细腻不等于演；先有事实，再有表达。
- 目前仍有句号/填充词问题，不回避。

## 六、情绪积累：一条消息决定不了她

### 6.1 快照里有什么

```json
{
  "schema": 2,
  "ts": 1794574664.8,
  "version": 2658,
  "source": "whale_affect",
  "stale_after": 300,
  "mood": "黏人",
  "intensity": 0.511,
  "valence": -0.123,
  "arousal": 0.511,
  "dominance": 0.387,
  "needs": {"bond": 96.0, "existence": 80.0, "mattering": 89.0, "energy": 51.7},
  "action": {"proactive_mult": 1.031, "reply_len_mult": 1.016, "first_delay_mult": 0.969,
             "meme_density": 0.319, "avoidance": 0.027, "topic_initiative": 0.548},
  "expression": {"source": "moodfusion-read-only"},
  "reason": "因为系统指标进了身体，黏人84，想凑近一点。",
  "observations": {"beams": {"label": "平静", "role": "observation"}}
}
```

### 6.2 怎么积累

- **每 60s 一拍**：身体/内感受/事件 → valence/arousal → needs 漂移。
- **事件触发**：对话/看到的东西/被夸/被冷落，都会改 valence/needs。
- **needs 是慢变量**：bond/existence/mattering/energy 不会一条消息就满/空。
- **快照版本递增**：`version` 从 2658 继续涨，旧快照过期 300s。
- **记忆/情绪峰值**：高显著事件进记忆和 peaks，之后还会被想起。
- **表达层读快照**：不是每条消息重新"演"，而是读当前累积状态。

### 6.3 一个例子

当前：bond 96/100、energy 51.7、valence −0.123、arousal 0.511、mood 黏人。  
原因：系统指标进了身体，黏人 84，想凑近一点。  
读方看到的是同一份：状态块、表情、闸门、网关，不会各说各话。

### 6.4 时间尺度

| 变量 | 尺度 | 说明 |
|---|---|---|
| valence/arousal | 秒–分钟 | 事件驱动，快 |
| needs | 分钟–小时 | 慢漂移 |
| bond/mattering | 小时–天 | 关系积累 |
| mood | 分钟 | 由底色+温度合成 |
| 记忆峰值 | 天 | 显著事件沉淀 |

## 七、完整流程（再压缩一遍）

```
启动：laya 8901 → 网关 8920 → 情绪内核 claim → 60s 主循环
每拍：身体/事件 → affect → moodfusion → snapshot
来消息：读 snapshot → 状态/表情/记忆 → prompt → 网关 → 模型 → 分段回复
失败：分类器回退词表；网关重连；快照过期读 legacy
回滚：改 shadow_switches.json / want_source，5s 热读
验收：快照/影子日志/闸门/网关 requests==injected
```

更细的时序见 [EMOTION-LOOP.md](EMOTION-LOOP.md)。

## 八、相比其他做法，强在哪

| 维度 | 常见做法 | 我们 | 代价 |
|---|---|---|---|
| 情绪一致性 | 多模块各算 | 单写者+快照 | 需要写者 claim |
| prompt 冲突 | 网关再注入一个心情 | 网关读同一份 | 网关要改/重启 |
| 回滚 | 改代码/重启 | 改 JSON 热读 | 需要开关纪律 |
| 情绪层次 | 一个标签 | 底色/温度/表达/扰动 | 实现更复杂 |
| 分类器 | 直接当结论 | 只做输入+回退 | 需要词表兜底 |
| 成本 | 黑箱不可控 | 本地分类+按需注入 | 需要自己运维 |
| 验真 | 感觉像 | 快照/日志/闸门 | 需要看日志 |

**一句话**：我们不是"模型更大"，是"把情绪当工程事实来管"。

## 十、诚实的边界

- 数字是本机实测，换机器/换模型会变。
- tokens 比例是估算，不同分词器有偏差。
- 价格会变，以官方账单为准。
- 延迟受网络/负载影响，12–28s 是观测范围，不是 SLA。
- 话术指标仍有句号/填充词问题，不粉饰。
- 这是框架预览，不是生产级服务。
