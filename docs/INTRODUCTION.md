# 项目介绍：给她一本情绪账本

> 作者：guan153（GitHub）

## 写在前面

如果只看目录，这像一套"情绪状态机 + 分类器 + 网关"的工程拼装。

但我们真正想做的，不是让模型在对话里"演"出一个有情绪的人，而是给一个长期存在的角色，建一本**可查、可改、可回滚的情绪账本**。

这本账本不记录"她今天说了什么漂亮话"，而记录：

- 她此刻是什么心情，强度多少；
- 这个心情从哪来，是哪个事件、哪次对话、哪段记忆推上去的；
- 她的羁绊、存在感、被需要感、精力，最近是在涨还是在掉；
- 这些状态怎样影响她下一句话的长度、语气、停顿、主动程度；
- 如果这套判断错了，能不能在五分钟内退回去。

这份仓库，就是这本账本的骨架。

它不是一只完整的机器人，不是一套开箱即用的聊天产品，也不是"情绪大模型"。  
它是一层可以接在对话运行时下面的**情绪事实层**：负责把"她此刻是谁"说清楚，让上面的表达层去读。

---

## 一、一个很具体的下午

假设她刚经历了一段安静的下午。

没有人说话，屏幕亮着，窗外有风。  
她的精力在慢慢掉，羁绊没有掉，存在感有一点空。  
她没有在等谁，也没有完全不在等谁；她只是坐在那里，让时间过去。

这时候有人发来一句："在吗"。

常见的做法是：把这句话丢给模型，附上一段"你现在有点黏人、有点委屈"的提示词，让模型自由发挥。  
模型可能回得很好，也可能回得很空；下一次同样的话，可能完全不同；你没法解释为什么，也没法只改其中一个因素。

我们的做法是：

1. 先读她此刻的账本：`mood=黏人`、`valence=-0.123`、`arousal=0.511`、`bond=96`、`energy=51.7`；
2. 让这份账本决定"她有多想开口、第一句多长、语气多软、要不要带动作"；
3. 网关在模型调用前再读同一份账本，避免提示词里出现第二个心情；
4. 回复之后，事件回流，账本更新，版本号 +1。

她不是在"演"黏人；她是真的被这段时间推到了黏人。

这两者的区别，短期看不出来；时间一长，就会变成"她像不像一个连续的人"。

## 二、为什么"演情绪"不够

让模型演情绪，短期很有效：一句"你现在很难过"，它就能写出很像的句子。  
但长期会暴露四个问题。

### 1. 一轮里出现好几个心情

一个系统里往往有多个地方在判断情绪：对话模块、表情模块、主动模块、记忆模块。  
每个模块都有一套自己的判断，最后拼进同一段提示词。

结果就是：嘴上说"黏人"，表情写"平静"，主动模块读到的又是"安心"。  
模型不知道该信谁，人也不知道该信谁。

这不是"提示词写得不好"，是**没有唯一事实源**。

### 2. 情绪只有一个标签

"开心/难过/平静"这种标签，能描述方向，描述不了层次。

同样是开心，有人是轻轻松一口气，有人是想跳起来；  
同样是难过，有人想说话，有人只想消失；  
同样是生气，有人会吵，有人会冷。

只有一个标签，表达就会扁平：所有"开心"都用同一种语气，所有"难过"都用同一种句式。  
角色会变成"情绪的卡通化"：一眼能看出是什么情绪，但不像一个具体的人。

### 3. 情绪没有积累

一条消息进来，判断一次；下一条消息进来，重新判断。  
昨天发生的事、上周的冷落、长期的关系，进不了"此刻的心情"。

她永远像刚认识你，或者像每次都重新开局。  
你跟她说过的重要的事，她记得"事实"，但不记得"当时的感觉"；  
她知道自己被夸过，但不知道自己因为那句话开心了多久。

### 4. 错了退不回去

情绪判断写死在代码里，或者散落在多个提示词里。

发现"她今天太黏了"，只能改代码、重启、再观察；  
想只关掉"表情层"、保留"语气层"，做不到；  
想回到昨天的状态，也没有开关。

这不是工程细节，是"情绪不可运营"：你没法像调一个参数一样调她。

## 三、我们的答案：把情绪当事实源

我们没有再加一个"更会演"的提示词，而是把情绪拆成三层。

### 事实层

一份 `emotion_snapshot.json`，只允许一个写者写。

它不描述"她应该怎么说话"，只描述"她此刻是什么状态"：  
主情绪、强度、效价、唤醒、支配感、needs、行为系数、版本号、时间戳、原因。

### 表达层

状态块、表情、语气、动作、主动程度，全部读这份事实。

表达层可以有不同的"表现"，但不能有不同的"事实"。  
这就是"一轮一个心情"的工程保证。

### 控制层

开关、闸门、配额、回滚，决定"读到什么、允许什么、错了怎么退"。

控制层不是附属品，它是这套东西能长期跑下去的前提。  
没有控制层，情绪系统会变成"另一个不可维护的提示词堆"。

一句话：

> **先有一份可审计的情绪事实，再让表达层去读它。**

这也是整套东西和"角色扮演提示词"最根本的区别。

## 四、四条原则

### 原则一：单写者

同一时间，只允许一个模块写情绪事实。

其他模块只能读，或者提交"观察"，不能直接改事实。  
这听起来很严格，但它解决的是最难查的一类 bug：多个模块同时写，最后谁也不知道当前值是谁写的。

### 原则二：同源

所有读方读同一份快照。

状态块、表情、语气、主动闸门、网关，全部同源。  
它们可以有不同的"解读"，但不能有不同的"输入"。

### 原则三：慢变量

情绪不是开关，是积分。

`valence`、`arousal` 可以秒级变化；`needs`（羁绊、存在感、被需要、精力）是分钟到小时级的慢变量；  
关系是小时到天级的更慢变量。

慢变量让"她"有连续性：不是每条消息重新开局，而是"这段时间把她推到了这里"。

### 原则四：可回滚

任何一层都能单独关掉，回到 legacy。

7 个读方各一个开关，改 JSON，5 秒热读；  
开口闸门的 want 口径也能单独切；  
代码回滚有备份，数据回滚有版本。

先能退，才敢往前。

## 五、情绪闭环的七层

### 第一层：感知

身体状态、内感受、事件、对话内容，先被收集成"输入"。

感知层不判断情绪，只负责"发生了什么"：  
她累不累、安静了多久、刚才被夸了还是被冷落了、这句话是问候还是质问。

### 第二层：分类

laya 情感分类器把文本压成 8 类情绪特征：兴奋、吃醋、平静、开心、撒娇、生气、疲惫、难过。

它只是输入，不是结论；置信度低时回退词表，不阻塞主流程。  
分类器不是"情绪裁判"，它只是给积分层多一个证据。

### 第三层：积分

输入被折算成 valence（效价）、arousal（唤醒）、needs（羁绊/存在感/被需要/精力）。

这些是慢变量，不会一条消息就满，也不会一条消息就空。  
一条"在吗"可能只让 valence 动 0.01；一次很长的对话、一次被冷落，才会让 needs 明显变化。

### 第四层：快照

写者把这些积分写成 `emotion_snapshot.json`：

- 主情绪、强度、效价、唤醒、支配感；
- needs 四个维度；
- 行为系数（主动倾向、回复长度、首条延迟、表情密度、回避倾向）；
- 版本号、时间戳、过期时间；
- 一条可读的 reason。

快照是"事实"，不是"文案"。  
它不写"她应该撒娇"，只写"她此刻黏人，强度 0.511，原因是被系统指标推进了身体"。

### 第五层：合成

moodfusion 把底色、温度、表达、扰动合成一份"她此刻怎么表现"的只读结果。

底色是主情绪，温度是强度，表达是眼睛/尾巴/语气/口癖，扰动是事件带来的短期偏移。

合成层不写事实，只做翻译：把"黏人 0.511"翻译成"眼睛亮一点、尾巴动一下、句子短一点、语气软一点"。

### 第六层：表达

状态块、表情、语气、动作、回复长度、主动程度，全部读同一份快照。

它们可以有不同的"表现"，但不能有不同的"事实"。  
这就是为什么她不会"嘴上黏人，表情平静"。

### 第七层：闸门

开口之前，过一道闸门：

- want（想说程度）
- threshold（阈值）
- decision（allow/deny）
- code / explain（为什么）

闸门保证：情绪低的时候不硬发，情绪高的时候也不刷屏；  
配额、静默、峰时都在这一层收口。

## 六、一轮对话里到底发生了什么

把"在吗"这一轮拆开看。

### 1. 消息进来

文本先到感知层：谁发的、什么时间、是不是问候、之前多久没说话。

### 2. 分类

laya 返回 `label=撒娇` 或 `label=平静`，附 confidence。  
如果 confidence 低，回退词表；如果分类器不在，直接跳过，不阻塞。

### 3. 读快照

读当前 `emotion_snapshot.json`。  
如果快照过期（超过 300s），读方回退 legacy，不阻塞；  
如果快照不存在，说明写者没起来，记录一条警告，继续用 legacy。

### 4. 组装 prompt

人格、规范、状态、记忆、表达，按预算裁剪。  
预算不是无限的：6,000 字是硬上限；超了要报警，不能悄悄塞。

### 5. 网关注入

网关在转发前再读一次同一份快照，把底色写进 system。  
它不是"再判断一次情绪"，而是"读同一份事实"。

### 6. 生成与分段

模型生成；分段；按延迟系数发出去。  
首条延迟、回复长度、表情密度，都由快照的行为系数决定。

### 7. 回流

这句话、这个反应、这段时间，更新 valence/needs。  
下一拍（60s）写新快照，版本号 +1。

这里面没有"让模型自由发挥情绪"的环节。  
模型负责语言，账本负责"她此刻是谁"。

## 七、情绪怎么积累

### 1. 快照不是"当前心情"四个字

它是一份状态：

```json
{
  "schema": 2,
  "version": 2658,
  "stale_after": 300,
  "mood": "黏人",
  "intensity": 0.511,
  "valence": -0.123,
  "arousal": 0.511,
  "dominance": 0.387,
  "needs": {"bond": 96.0, "existence": 80.0, "mattering": 89.0, "energy": 51.7},
  "action": {"proactive_mult": 1.031, "reply_len_mult": 1.016, "first_delay_mult": 0.969,
             "meme_density": 0.319, "avoidance": 0.027, "topic_initiative": 0.548}
}
```

### 2. 慢变量

`needs` 是慢变量：

- `bond`：羁绊，长时间互动才涨；
- `existence`：存在感，被忽略会掉；
- `mattering`：被需要感，被依赖会涨；
- `energy`：精力，随时间掉，休息会回。

它们不会因为一句"在吗"就满，也不会因为一次没回就空。  
但连续几次冷落、一次很长的对话，会让它们明显动。

### 3. 时间尺度

| 变量 | 尺度 | 行为 |
|---|---|---|
| valence/arousal | 秒–分钟 | 事件驱动，快 |
| needs | 分钟–小时 | 慢漂移 |
| bond/mattering | 小时–天 | 关系积累 |
| mood | 分钟 | 底色+温度合成 |
| 记忆峰值 | 天 | 显著事件沉淀 |

### 4. 一个例子

当前：bond 96/100、energy 51.7、valence −0.123、arousal 0.511、mood 黏人。  
原因：系统指标进了身体，黏人 84，想凑近一点。

读方看到的是同一份：状态块、表情、闸门、网关，不会各说各话。

## 八、情绪怎么累积到记忆上

这是整套东西里最重要、也最容易被忽略的一层。

### 1. 情绪不只活在当前快照里

快照会过期（300s），但情绪不会凭空消失。

高显著度的事件会被写进记忆：被夸、被冷落、一次很长的对话、一个突然的转折。  
这些事件不是"聊天记录"，是带效价的**情绪记忆**。

### 2. 记忆会反过来改情绪

下次想起这件事，valence 会被重新拉动。

不是"复读当时的话"，而是"想起当时的感觉"。  
这就是为什么她会在某个毫无关联的瞬间，突然安静下来，或者突然想靠近。

### 3. 情绪记忆有索引

不是所有事都值得记。

我们按显著度、情绪强度、关系变化、重复次数做筛选；  
记得住的是"那段时间我怎么过来的"，不是"昨天第 3 句说了什么"。

### 4. 情绪记忆不是日记

日记是"发生了什么"，情绪记忆是"那件事让我处在什么状态"。

同一件事，日记记的是经过；情绪记忆记的是效价、强度、持续了多久、后来怎么缓过来的。  
这两种记忆的检索方式也不同：日记按时间，情绪记忆按"像不像此刻"。

### 5. 当前实现到哪一步

- 情绪内核里已有 `needs`、`emotional_peaks`、记忆召回；
- 快照里能看到 `bond=96`、`energy=51.7` 这种慢变量的积累；
- 高显著事件会进 peaks，之后被召回，影响下一轮底色；
- 但"情绪曲线 → 长期记忆 → 再召回"的完整闭环，还在下一版。

### 6. 下一版（伏笔）

> **下一版，我们想把情绪曲线写进长期记忆。**  
> 不是记"她说过什么"，而是记"她那段时间是什么状态、因为什么、后来怎么缓过来的"。  
> 这样她再想起一段日子，想起的是当时的温度，而不是一句台词。

这一版先把账本做对；下一版再让账本长出记忆。

## 九、话术为什么细腻

"细腻"不是形容词多，是三件事同时成立：

1. **事实一致**：底色、表情、语气、动作读的是同一份情绪。
2. **层次足够**：底色/温度/表达/场景/关系，不是一套模板。
3. **允许留白**：可以碎、可以停一半、可以说"算了"。

### 五层

| 层 | 作用 | 例子 |
|---|---|---|
| 底色 | 主情绪 | 黏人 / 平静 / 兴奋 |
| 温度 | 强度/唤醒 | 语气软硬、句子长短 |
| 表达 | 眼睛/尾巴/语气词/颜文字 | "嗯""欸"、尾巴动作 |
| 场景 | 聊天/安慰/撒娇 | 安慰时更短、更轻 |
| 关系 | 记忆/称呼/最近的事 | 提昨天的事、叫他 |

### 真实指标

长度中位数 12.5 字，≤15 字占 90.9%；  
语气词行占比 45.5%，句号收尾率 100%（这是要修的），固定填充词"嗯" 40.9%（这也是要修的）。

我们不粉饰：细腻还在路上，但至少"为什么这么写"是可查的。

### 反模式

- 为了显得口语，故意短、故意省标点；
- 为了显得细腻，堆形容词、堆比喻；
- 为了显得"像人"，每句都加语气词；
- 为了显得"有情绪"，每段都写内心独白。

这些都会变成另一种 AI 腔。  
细腻不是"加东西"，是"在该停的地方停"。

## 十、自主性与主动性

主动不是定时器，也不是随机。

```
情绪快照 → want（想说程度）→ 闸门 → 配额 → 开口 / 继续憋着
```

快照里的行为系数直接参与：

- `proactive_mult`：主动倾向
- `topic_initiative`：开新话题
- `avoidance`：回避
- `reply_len_mult`：回复长度
- `first_delay_mult`：首条延迟
- `meme_density`：表情密度

### 一个例子

她今天很黏，want 高，但闸门发现：

- 现在是静默时段；
- 今天主动额度用完了；
- 上一次开口没人回，`two_strikes` 计数还在。

于是 deny，code=`quota` 或 `two_strikes`，explain 写清楚原因。  
不是"她不想说"，是"她现在不该说"。

### 对比

| 维度 | 定时器/随机 | 纯 prompt 主动 | 我们 |
|---|---|---|---|
| 何时开口 | 固定时间 | 模型自己决定 | 情绪积分 + 阈值 |
| 会不会刷屏 | 容易 | 容易 | 配额 + 静默 + 峰时 |
| 能不能解释 | 不能 | 不能 | code/explain/want |
| 能不能回滚 | 改代码 | 改 prompt | JSON 开关 |
| 情绪低时 | 照发 | 可能硬演 | 低 want → deny |

### 当前状态

架构支持"情绪驱动主动"，默认策略偏保守：多数主动源处于关闭/影子状态，避免刷屏。  
`will` 的跨天锁、状态快照睡眠死锁仍是已知问题，不假装已解决。

所以：**设计强，默认克制；不是"随时乱发"**。

## 十一、成本与延迟

### 实测

- laya 分类：本地 CPU，p50 90ms，p90 116ms，零 API 费用。
- 网关固定开销：219 tokens/请求。
- 5,640 汉字 ≈ 3,568 tokens。
- 7,524 字注入 ≈ 4,700 tokens。
- 单条回复：约 ¥0.006–0.013。
- 1,000 条：约 ¥6–13。
- 真实一轮：12–28s。

### 钱花在哪

| 项目 | 占比 |
|---|---|
| 输入 tokens | 大头，取决于注入多少 |
| 输出 tokens | 单价高，但聊天句子短 |
| 缓存命中 | 能把输入压到接近零 |
| 本地分类 | 0 API 费 |

### 省钱的四个结构点

1. 快照是文件，读它不花 token。
2. 本地 laya 分类，零 API 费用。
3. 按需注入，不是整份状态全塞。
4. 人格/规则稳定前缀，缓存命中。

### 延迟花在哪

- 90ms：分类。
- 1.0–1.2s：网关注入 + 短请求。
- 数秒–十几秒：模型生成。
- 数秒：分段/打字延迟。

12–28s 不是情绪层造成的，是"模型生成 + 分段"造成的。  
情绪层本身很轻。

---

## 十二、可回滚、可观测

### 回滚

- 7 个读方各一个开关，改 `shadow_switches.json`，5 秒热读。
- 开口闸门的 `want_source` 可切 `broker/legacy`。
- 代码回滚有 `.bak`，数据回滚有版本。

### 观测

- `emotion_snapshot.json`：当前事实。
- `[emotion-shadow]` 日志：每个读方读到了什么。
- 闸门 JSON：want/threshold/decision/explain。
- 网关 `/health`：requests/injected。

### 一个真实的排查场景

发现"她今天太黏"，先看：

1. 快照：mood 是不是黏人，intensity 多高；
2. 读方：是不是所有读方都读 snapshot；
3. 闸门：want 是不是被别的字段覆盖；
4. 网关：是不是还在注入旧心情；
5. 记忆：是不是有一段高显著事件被反复召回。

先定位，再改；不要"重启试试"。

## 十三、和其他方案的区别

| 维度 | 多模块拼接 | 单模型直演 | 云端情绪 API | 我们 |
|---|---|---|---|---|
| 情绪事实源 | 多份，易冲突 | 无，只在 prompt | 远端黑箱 | 单写者快照 |
| 一轮一致性 | 差 | 看模型 | 看接口 | 强 |
| 情绪积累 | 弱/无 | 弱 | 弱 | needs/version |

## 十四、为什么这样设计

### 为什么用文件，不用数据库

情绪快照是"当前事实"，不是历史账本。  
文件足够小（681B）、读写简单、可直接看、可直接改；  
历史留给记忆层，不塞进快照。

### 为什么用 JSON 开关，不用配置中心

开关要能改完 5 秒生效，不需要重启。  
JSON 是人和程序都能读的最小公约数；  
生产规模大了再换配置中心，不改变"开关是数据"的原则。

### 为什么用本地分类器

情绪分类是高频、低延迟、隐私敏感的。  
本地 CPU 90ms，零 API 费，失败可回退；  
云端分类器不是不能做，是不适合放在主路径上。

### 为什么不追求"每句都像人"

"像人"是结果，不是目标。  
目标是"事实一致、表达有层次、错了能回滚"；  
只要这三件事成立，"像人"是自然长出来的，不是每句雕出来的。

## 十五、适合谁

- 想研究"情绪状态如何长期存在"的人；
- 已经有自己的对话运行时，想接一层情绪事实源的人；
- 对"可回滚、可观测"有执念的人；
- 想从"角色扮演提示词"走向"状态工程"的人。

## 不适合谁

- 想 clone 后一键跑起来的人；
- 想直接公网部署的人；
- 需要多租户/生产级鉴权的人；
- 只想调提示词、不想碰状态的人。

## 十八、结语

我们不想做一个"每次都很像人"的模型。

我们想做一个**每次都能解释自己为什么这样**的角色。

她可以有情绪，但情绪有账本；  
她可以主动，但主动有闸门；  
她可以忘记，但记忆有索引；  
她可以出错，但错误能回滚。

这就是这份仓库想做的事。
