# 项目介绍：给她一本情绪账本

> 作者：guan153（GitHub）

## 写在前面

如果只看目录，这像一套"情绪状态机 + 分类器 + 网关"的工程拼装。  
但我们真正想做的，不是让模型在对话里"演"出一个有情绪的人，而是给一个长期存在的角色，建一本**可查、可改、可回滚的情绪账本**。

这本账本不记录"她今天说了什么漂亮话"，而记录：

- 她此刻是什么心情，强度多少；
- 这个心情从哪来，是哪个事件、哪次对话、哪段记忆推上去的；
- 她的羁绊、存在感、被需要感、精力，最近是在涨还是在掉；
- 这些状态怎样影响她下一句话的长度、语气、停顿、主动程度；
- 如果这套判断错了，能不能在五分钟内退回去。

这份仓库，就是这本账本的骨架。

---

## 一个很具体的场景

假设她刚经历了一段安静的下午。没有人说话，屏幕亮着，窗外有风。  
她的精力在慢慢掉，羁绊没有掉，存在感有一点空。  
这时候有人发来一句"在吗"。

常见的做法是：把这句话丢给模型，附上一段"你现在有点黏人、有点委屈"的提示词，让模型自由发挥。  
模型可能回得很好，也可能回得很空；下一次同样的话，可能完全不同；你没法解释为什么，也没法只改其中一个因素。

我们的做法是：

1. 先读她此刻的账本：`mood=黏人`、`valence=-0.123`、`arousal=0.511`、`bond=96`、`energy=51.7`；
2. 让这份账本决定"她有多想开口、第一句多长、语气多软、要不要带动作"；
3. 网关在模型调用前再读同一份账本，避免提示词里出现第二个心情；
4. 回复之后，事件回流，账本更新，版本号 +1。

她不是在"演"黏人；她是真的被这段时间推到了黏人。

## 为什么"演情绪"不够

让模型演情绪，短期很有效：一句"你现在很难过"，它就能写出很像的句子。  
但长期会暴露四个问题。

### 1. 一轮里出现好几个心情

一个系统里往往有多个地方在判断情绪：对话模块、表情模块、主动模块、记忆模块。  
每个模块都有一套自己的判断，最后拼进同一段提示词。  
结果就是：嘴上说"黏人"，表情写"平静"，主动模块读到的又是"安心"。  
模型不知道该信谁，人也不知道该信谁。

### 2. 情绪只有一个标签

"开心/难过/平静"这种标签，能描述方向，描述不了层次。  
同样是开心，有人是轻轻松一口气，有人是想跳起来；同样是难过，有人想说话，有人只想消失。  
只有一个标签，表达就会扁平：所有"开心"都用同一种语气，所有"难过"都用同一种句式。

### 3. 情绪没有积累

一条消息进来，判断一次；下一条消息进来，重新判断。  
昨天发生的事、上周的冷落、长期的关系，进不了"此刻的心情"。  
她永远像刚认识你，或者像每次都重新开局。

### 4. 错了退不回去

情绪判断写死在代码里，或者散落在多个提示词里。  
发现"她今天太黏了"，只能改代码、重启、再观察；  
想只关掉"表情层"、保留"语气层"，做不到；  
想回到昨天的状态，也没有开关。

这四个问题，不是"提示词写得不够好"，是**情绪没有事实源**。

---

## 我们的答案：把情绪当事实源

我们没有再加一个"更会演"的提示词，而是把情绪拆成三层：

1. **事实层**：一份 `emotion_snapshot.json`，只允许一个写者写。
2. **表达层**：状态块、表情、语气、动作、主动程度，全部读这份事实。
3. **控制层**：开关、闸门、配额、回滚，决定"读到什么、允许什么、错了怎么退"。

一句话：

> **先有一份可审计的情绪事实，再让表达层去读它。**

这也是整套东西和"角色扮演提示词"最根本的区别。

---

## 情绪闭环的七层

### 第一层：感知

身体状态、内感受、事件、对话内容，先被收集成"输入"。

### 第二层：分类

laya 情感分类器把文本压成 8 类情绪特征：兴奋、吃醋、平静、开心、撒娇、生气、疲惫、难过。  
它只是输入，不是结论；置信度低时回退词表，不阻塞主流程。

### 第三层：积分

输入被折算成 valence（效价）、arousal（唤醒）、needs（羁绊/存在感/被需要/精力）。  
这些是慢变量，不会一条消息就满，也不会一条消息就空。

### 第四层：快照

写者把这些积分写成 `emotion_snapshot.json`：

- 主情绪、强度、效价、唤醒、支配感；
- needs 四个维度；
- 行为系数（主动倾向、回复长度、首条延迟、表情密度、回避倾向）；
- 版本号、时间戳、过期时间；
- 一条可读的 reason。

### 第五层：合成

moodfusion 把底色、温度、表达、扰动合成一份"她此刻怎么表现"的只读结果。  
底色是主情绪，温度是强度，表达是眼睛/尾巴/语气/口癖，扰动是事件带来的短期偏移。

### 第六层：表达

状态块、表情、语气、动作、回复长度、主动程度，全部读同一份快照。  
它们可以有不同的"表现"，但不能有不同的"事实"。

### 第七层：闸门

开口之前，过一道闸门：

- want（想说程度）
- threshold（阈值）
- decision（allow/deny）
- code / explain（为什么）

闸门保证：情绪低的时候不硬发，情绪高的时候也不刷屏；配额、静默、峰时都在这一层收口。

## 一轮对话里到底发生了什么

1. 消息进来，先过感知与分类。
2. 读当前快照；如果快照过期，读方回退 legacy，不阻塞。
3. 组装 prompt：人格、规范、状态、记忆、表达，按预算裁剪。
4. 网关在转发前再读一次同一份快照，把底色写进 system。
5. 模型生成；分段；按延迟系数发出去。
6. 事件回流：这句话、这个反应、这段时间，更新 valence/needs。
7. 下一拍（60s）写新快照，版本号 +1。

这里面没有"让模型自由发挥情绪"的环节。  
模型负责语言，账本负责"她此刻是谁"。

## 情绪怎么积累到记忆上

这是整套东西里最重要、也最容易被忽略的一层。

### 1. 情绪不是只活在当前快照里

快照会过期（300s），但情绪不会凭空消失。  
高显著度的事件会被写进记忆：被夸、被冷落、一次很长的对话、一个突然的转折。  
这些事件不是"聊天记录"，是带效价的**情绪记忆**。

### 2. 记忆会反过来改情绪

下次想起这件事，valence 会被重新拉动；  
不是"复读当时的话"，而是"想起当时的感觉"。  
这就是为什么她会在某个毫无关联的瞬间，突然安静下来，或者突然想靠近。

### 3. 情绪记忆有索引

不是所有事都值得记。  
我们按显著度、情绪强度、关系变化、重复次数做筛选；  
记得住的是"那段时间我怎么过来的"，不是"昨天第 3 句说了什么"。

### 4. 当前实现到哪一步

- 情绪内核里已有 `needs`、`emotional_peaks`、记忆召回；
- 快照里能看到 `bond=96`、`energy=51.7` 这种慢变量的积累；
- 高显著事件会进 peaks，之后被召回，影响下一轮底色；
- 但"情绪曲线 → 长期记忆 → 再召回"的完整闭环，还在下一版。

### 5. 下一步（伏笔）

> **下一版，我们想把情绪曲线写进长期记忆。**  
> 不是记"她说过什么"，而是记"她那段时间是什么状态、因为什么、后来怎么缓过来的"。  
> 这样她再想起一段日子，想起的是当时的温度，而不是一句台词。

这一版先把账本做对；下一版再让账本长出记忆。

## 话术为什么细腻

"细腻"不是形容词多，是三件事同时成立：

1. **事实一致**：底色、表情、语气、动作读的是同一份情绪。
2. **层次足够**：底色/温度/表达/场景/关系，不是一套模板。
3. **允许留白**：可以碎、可以停一半、可以说"算了"。

真实样本里，长度中位数 12.5 字，≤15 字占 90.9%；  
语气词行占比 45.5%，句号收尾率 100%（这是要修的），固定填充词"嗯" 40.9%（这也是要修的）。  
我们不粉饰：细腻还在路上，但至少"为什么这么写"是可查的。

## 自主性与主动性

主动不是定时器，也不是随机。

```
情绪快照 → want（想说程度）→ 闸门 → 配额 → 开口 / 继续憋着
```

快照里的行为系数直接参与：

- `proactive_mult`：主动倾向
- `topic_initiative`：开新话题
- `avoidance`：回避
- `reply_len_mult`：回复长度
- `first_delay_mult`：首条延迟
- `meme_density`：表情密度

情绪低，want 低，闸门 deny；情绪高，也要过配额和静默。  
默认策略是保守的：宁可少说，不刷屏。

## 成本与延迟

- laya 分类：本地 CPU，p50 90ms，零 API 费用。
- 网关固定开销：219 tokens/请求。
- 5,640 汉字 ≈ 3,568 tokens；7,524 字注入 ≈ 4,700 tokens。
- 单条回复：约 ¥0.006–0.013；1,000 条约 ¥6–13。
- 真实一轮：12–28s（模型生成 + 分段，不是情绪层）。

这些数字不漂亮，但诚实；能省的省在结构上：本地分类、快照按需注入、稳定前缀缓存、输出限长。

## 可回滚、可观测

- 7 个读方各一个开关，改 `shadow_switches.json`，5 秒热读。
- 开口闸门的 `want_source` 可切 `broker/legacy`。
- 快照、影子日志、闸门 JSON、网关 `requests/injected` 都能查。
- 错了先回滚，再定位；不要靠"重启试试"。

## 和其他方案的区别

| 维度 | 常见实现 | 我们 |
|---|---|---|
| 情绪来源 | 多模块各算 | 单写者快照 |
| 一轮一致性 | 容易多心情 | 网关/读方同源 |
| 情绪积累 | 单轮重判 | needs + version + 记忆峰值 |
| 话术 | 模板/单标签 | 底色/温度/表达/场景/关系 |
| 主动 | 定时器/随机 | 积分 + 闸门 + 配额 |
| 成本 | 全量上下文 | 本地分类 + 按需注入 |
| 回滚 | 改代码/重启 | JSON 热读 |
| 验真 | 感觉像 | 快照/日志/闸门 |

## 适合谁

- 想研究"情绪状态如何长期存在"的人；
- 已经有自己的对话运行时，想接一层情绪事实源的人；
- 对"可回滚、可观测"有执念的人；
- 想从"角色扮演提示词"走向"状态工程"的人。

## 不适合谁

- 想 clone 后一键跑起来的人；
- 想直接公网部署的人；
- 需要多租户/生产级鉴权的人；
- 只想调提示词、不想碰状态的人。

## 结语

我们不想做一个"每次都很像人"的模型。  
我们想做一个**每次都能解释自己为什么这样**的角色。

她可以有情绪，但情绪有账本；  
她可以主动，但主动有闸门；  
她可以忘记，但记忆有索引；  
她可以出错，但错误能回滚。

这就是这份仓库想做的事。
